## 账号池分组删除兼容旧 sidecar 404
- 用户反馈正式版账号池点击“移除本组”后提示 `SIDECAR 请求失败 (404): 404 NOT FOUND`，组和账号都没有消失。
- 根因定位：分组删除和 selected bulk delete 都统一走 `DeleteAccountsBatch -> POST /v0/management/accounts/batch-delete`；该路由是 2026-06-09 新增的，正式版 bundle 若仍携带旧 sidecar，就会在批量删除入口直接 404。
- 修复：`internal/wailsapp/accounts.go` 的 `DeleteAccountsBatch` 遇到 sidecar 404 时，自动降级为逐账号 `DELETE /v0/management/accounts/:id`，继续返回批量成功/失败摘要，并保持删除成功后的 cache prune / 列表刷新语义。
- 回归：新增 `TestDeleteAccountsBatchFallsBackToSingleDeleteWhenBatchRouteMissing`，验证请求顺序、成功/失败汇总和 auth metadata cache 清理；`go test ./internal/wailsapp -run 'TestDeleteAccountsBatchUsesBatchManagementAPI|TestDeleteAccountsBatchFallsBackToSingleDeleteWhenBatchRouteMissing' -count=1` 通过。
- 沉淀：更新 `.agents/skills/gettokens-domain-engineering/SKILL.md`，约束“新增 sidecar management endpoint 落在既有热路径时，Wails/root 必须考虑旧 sidecar 404 的兼容降级，而不是把缺路由直接暴露给 UI”。

## macOS 26.x 在线更新兼容降级
- 用户通过正式版 app 内在线更新后，系统弹出“GetTokens.app 已损坏，无法打开”，触发场景是 Sparkle 原生更新入口，不是手动下载 DMG。
- 证据链：正式版 `v1.2.1` 的 DMG、`codesign`、`spctl`、`stapler`、`syspolicy_check distribution` 都通过；但 GUI 启动日志出现 `ASP: Security policy would not allow process`。
- 对照实验显示：保留 `com.apple.provenance` 的 app 副本无法稳定启动；去掉 `com.apple.provenance` / `com.apple.macl` 的副本可以启动，说明更像 macOS `26.x` 对 Sparkle 更新后 app 的 provenance/runtime policy 拦截。
- 产品修复：`internal/wailsapp` 把“Sparkle framework 可用”与“当前机器允许原生更新 UI”拆开；在 macOS major version `>= 26` 时，即使 Sparkle 可用也强制回退到 GitHub Release 下载页，不再向用户暴露原生在线更新入口。
- 回归测试：新增 `internal/wailsapp/app_test.go`，覆盖 Darwin 版本解析、原生更新 UI 启用门槛和 Wails 暴露的更新能力开关。
