# 2026-06-01

## Account quota refresh no-change diagnosis
- 现象：账号卡片点击额度刷新后数值没有变化。
- 运行态证据：`/Users/linhey/.config/gettokens/sidecar.log` 在 00:32 后反复记录 `GET /v0/management/accounts` 返回 500；直接请求 sidecar 复现错误 `ensure account store metadata: database is locked (SQLITE_BUSY)`。
- 锁持有证据：`lsof /Users/linhey/.config/gettokens/accounts-v1.sqlite` 显示 `TablePro` 与当前 `cli-proxy-api` 同时打开账号库。
- 关联改动：2026-05-31 的 sidecar-native quota refresh 改动后，Codex API key 额度刷新依赖 sidecar `quota-refresh` 与账号 SQLite；`internal/wailsapp/quota.go` 在刷新失败时会尝试返回已有 `quota-status` 缓存，因此 UI 可能表现为“刷新成功但额度不变”。
- 结论：当前首要根因是账号 SQLite 被锁导致 sidecar 账号读取失败；最近改动扩大了账号 store 与 sidecar runtime 的依赖面，并让失败更容易被旧缓存掩盖。
- 后续风险：需要考虑让账号 store schema/metadata 初始化避免每次读请求写库，或为刷新失败显式透出 degraded/error 状态，避免卡片静默显示旧额度。

## Account store SQLite治理落地
- 已在 CLIProxyAPI fork 将 management handler 的 account store 改为生命周期级复用：首次打开时 `EnsureSchema`，后续请求复用已初始化 store；`SetAccountStorePath` 切换路径时关闭旧 store 并清缓存。
- 已为 `accounts-v1.sqlite` 增加 WAL pragma，并将 account store 连接池限制为 `MaxOpenConns=1 / MaxIdleConns=1`，先消除 sidecar 内部自发写竞争，再按证据评估是否需要更细的读写连接拆分。
- 已在 Wails Codex API key quota refresh 缓存兜底路径标记 `stale=true`，并把刷新失败原因写入 `degradedReason`，避免账号卡片继续把旧额度显示成 fresh success。
- 验证：新增红灯测试 `TestOpenAccountStoreReusesInitializedStoreWhenExternalWriterHoldsLock` 和 `TestGetCodexQuotaMarksCachedUnifiedQuotaStaleWhenRefreshFails`，并通过 CLIProxyAPI accountstore/management、GetTokens wailsapp/cliproxyapi、前端 unit/typecheck 回归。
- 沉淀：新增 `docs-linhay/dev/20260601-account-store-sqlite-governance.md`，并更新 `gettokens-domain-engineering` skill；不更新 `AGENTS.md`，因为该规则属于账号/quota 领域边界，不是全仓通用治理。
