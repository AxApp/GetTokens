## Claude Code open-response 兼容性研究立项
- 用户追问 “我们支持 claude code 对接 open-response 格式吗？”，随后要求开一个独立 space 研究。
- 已新建 `docs-linhay/spaces/20260615-claude-code-open-responses/`，并补充研究边界、证据门禁与后续问题清单。
- 继续深挖运行时后，当前结论已收紧为：
  - Claude Code ingress 固定 `/v1/messages`，Wails probe 也只打 Anthropic Messages。
  - Claude handler 运行时 `SourceFormat=claude`，若命中 openai-compatible provider，更像是“Claude 请求转 OpenAI Chat upstream”。
  - `openai/claude` translator 已存在，说明 `Claude -> OpenAI Chat` 方向有代码路径。
  - 但没有找到 `Claude -> OpenAI Responses` 主链路；`claude/openai/responses` 实际是 `OpenAI Responses -> Claude` 方向。
- 当前对用户的安全口径应是：**不支持 Claude Code 对接 open-response 作为正式能力**；若后续要做，需要补 translator 注册、executor `/responses` path 与 focused tests，而不是只拿参考代码当依据。
- 本轮进一步补齐了文件级实现缺口：当前阻塞不仅在 translator，还包括 Claude channel 候选筛选、Wails probe/evidence、frontend 文案和能力标记。已经把缺口清单与验收草稿写回 `20260615-claude-code-open-responses` space，后续进入实现时可直接按该清单拆任务。
- 继续往下收敛后，又新增了一份函数级蓝图：把 Claude handler、BaseAPIHandler、OpenAICompatExecutor、translator 注册点、Wails probe 和建议新增的 focused test 名都列出来了。现在这份 space 已经能直接作为后续开发切片的任务底稿使用。
- 本轮再往前推了一步，补了风险评估：当前最高风险面是 `Claude -> OpenAI Responses` translator 缺失、stream 事件兼容、tool call / tool_result 闭环，以及 OpenAI-compatible executor 的 `/responses` path；usage、error mapping、Wails 候选与 UI 收口属于次级风险。后续如果要实现，应按这个优先级排，不建议先动 UI 再补 runtime。
