## 账号池 WebContent 内存回升

- 证据：用户反馈 Activity Monitor 中 `wails://wails` 达到约 1GB；只读排查确认 pid `38725` 是 `/Applications/GetTokens.app` 的 WebKit WebContent。`vmmap -summary 38725` 显示 Physical footprint `1.0G`、peak `1.8G`，主要在 `WebKit Malloc`，不是 sidecar Go heap。生产 sidecar pid `38727` RSS 约 188MB。
- 根因链路：账号页打开 1179 个账号时，生产日志显示每 30 秒自动请求 `rate-limit-strategies`、`rate-limit-status`、6 批 `quota-status?account_keys=[redacted:200]` + 1 批 `[redacted:179]`、以及 `usage-attribution?bucket=1h&include_unresolved=true&window=24h`；页面加载后的 supplemental sync 与 runtime sync effect 还会重复立即跑一次。LocalStorage key 本体约数 MB，但 `com.wails.GetTokens` LocalStorage WAL 出现 144MB，说明 quota/list cache 整包写入被轮询放大。

- 沉淀：更新 `.agents/skills/gettokens-performance-governance/SKILL.md`，记录大账号池自动 runtime sync 自适应频率、避免加载后重复 whole-pool sync、以及 timestamp-only cache 写入会放大 WebKit WAL 的性能边界。

## 账号 auth-error auto-refresh 持久化修复

- 背景：用户重启 dev app 后反馈 K12 组只有 2 个账号异常，预期整组异常。证据：K12 组 875 个账号，`runtimeStates` 只命中 2 个 K12 `auth-error`，`quota-status` 对 875 个 K12 keys 也只返回 2 个 `blocked=true`；sidecar 启动日志同时出现批量 `invalid_refresh_token / refresh_token_reused / refresh_token_invalidated` auto-refresh 失败。
- 根因：`Manager.refreshAuth()` 在 refresh 失败时只更新 auth manager 内存状态，没有触发 `OnAuthUpdated` hook；GetTokens `AccountRouteGuardResultHook.OnAuthUpdated()` 也没有把 `auth.LastError=unauthorized` 的终态 OAuth refresh failure 转成 account-scoped `auth-error`。所以启动期发现的 K12 凭证失效没有进入 route guard / quota-status，只剩历史已持久化的 2 个可见异常。
- 实现：CLIProxyAPI `sdk/cliproxy/auth.Manager.refreshAuth()` 在失败状态落盘到内存后通知 hook；`internal/gettokenshooks.AccountRouteGuardResultHook.OnAuthUpdated()` 将 401/unauthorized auth state 写入 `auth-error` route guard。真实请求失败、quota runtime denied、auto-refresh 终态失败现在进入同一条 persisted runtime state 链路。
- 验证：新增红灯测试后修复，`go test ./sdk/cliproxy/auth -run 'TestManager_RefreshAuthInvalidRefreshTokenNotifiesAuthUpdatedHook|TestManager_RefreshAuthInvalidRefreshTokenStopsAutoRefreshRetry' -count=1`、`go test ./internal/gettokenshooks -run 'TestAccountRouteGuardResultHookBlocksTerminalOAuthRefreshFailureOnAuthUpdated|TestSetChannelRoutingPolicyConfigPathHydratesPersistedRuntimeStatesForQuotaStatus' -count=1`、`go test ./sdk/cliproxy/auth -count=1`、`go test ./internal/gettokenshooks -count=1`、`./scripts/ensure-sidecar.sh darwin arm64` 通过。当前运行中的 dev sidecar 仍需重启后加载新逻辑并重新执行 auto-refresh 才能把整组失败写入 `runtimeStates`。
- 沉淀：更新 `.agents/skills/gettokens-domain-engineering/SKILL.md` 与 `docs-linhay/spaces/20260609-account-card-401-status/README.md`；这是账号/OAuth/sidecar route guard 领域规则，不升级 `AGENTS.md`。

## 账号 auth-error provider identity 传播修复

- 背景：继续验收发现 K12 组重启后仍只有 2 个账号异常；进一步查明 K12 875 个账号中有 675 个共享同一个 OpenAI `auth_json.account_id=7bf3a2ce-3298-40b0-ac9b-3c922a5a91a6`。截图中的绿色 sibling 卡和红色 Abeb/Accola 都属于这个 provider account identity。
- 根因：route guard 只按单个 `acct_*` / auth id / auth-file lookup，历史 `token_invalidated` 只持久化在两张卡的 `acct_*` 上。sibling access token 尚未触发 auto-refresh，因此不会自己写入失败，`quota-status` 也无法通过 provider identity 命中已有终态失败。
- 实现：CLIProxyAPI sidecar 新增 account-store identity resolver，从 auth-file `auth_json.account_id / chatgpt_account_id` 派生 `openai-account-id:<id>` / `provider-account-id:openai:<id>` lookup key；写入、水合、候选过滤和 management `quota-status` 查询都按该 identity 扩展；`quota-status` sources 去重，避免同一 reason 重复展示。
- 验证：`go test ./internal/gettokenshooks -count=1`、`go test ./sdk/cliproxy/auth -count=1`、`./scripts/ensure-sidecar.sh darwin arm64` 通过；重启 `./scripts/wails-cli.sh dev` 后 dev sidecar `BuiltAt: 2026-07-08T07:54:52Z`，真实 API 验收 K12 `total=875`、`blocked=675`、`authError=675`、共享 OpenAI account identity `675/675` blocked，`maxSourcesPerBlocked=1`。

## OpenRouter `tencent/hy3:free` 正式环境诊断

- 用户要求排查正式环境 OpenRouter 卡片为什么请求 `tencent/hy3:free` 不通，并允许复制 prod 数据到 dev/repro 环境大胆测试。
- 证据：prod `accounts-v1.sqlite` 中标题为 `OpenRouter` 的卡片实际是 `kind=codex-api-key`、`provider=codex`、`base_url=https://openrouter.ai/api`，`models_json=[{"name":"tencent/hy3:free","alias":""}]`；当前 DB 状态为 `disabled=1`。
- 复现：使用正式版 sidecar 二进制 + 隔离 profile `~/.config/gettokens-dev-hy3-repro/` 启动 repro。直打 `https://openrouter.ai/api/v1/responses` 同一把 key 请求 `tencent/hy3:free` 返回 `200`，响应模型规范化为 `tencent/hy3-20260706:free`；走 repro sidecar `POST /v1/responses` 同请求返回 `502 unknown provider for model tencent/hy3:free`。
- 根因：不是 OpenRouter 上游不可用，而是 GetTokens/CLIProxyAPI 对 `codex-api-key` 路径的 runtime model 注册边界。`synthesizeAccountStoreCodexKey()` 仅把 `models_json` 摘要成 `models_hash`，`registerModelsForAuth()` 的 `case "codex"` 只注册内置 Codex catalog / config codex models，不消费该卡片的自定义 `models_json`，因此 `tencent/hy3:free` 从未进入 global model registry。
- 中间验证：曾短暂实现过 runtime 兼容合成，并在 dev repro 中证明把误分类 OpenRouter 卡升格为 compat auth 后可请求成功；这只作为根因验证证据保留，不是最终方案。
- 用户随后明确“不需要 legacy，可以重新删除配置这些账号”。最终实现改为产品边界治理：已知 OpenAI-compatible provider 不能再以 `codex-api-key` 写入；存量误分类卡只审计、隔离并提示删除重建，不在 runtime 自动升格。
- 最终验证：`go test ./internal/gettokens/accountstore ./internal/watcher/synthesizer ./internal/api/handlers/management ./sdk/cliproxy -count=1` 与 `./scripts/ensure-sidecar.sh darwin arm64` 通过。重建 sidecar `BuiltAt=2026-07-08T09:39:34Z` 使用 dev repro profile 验证：diagnostics 命中 `OpenRouter` 1 张误分类卡；`GET /v1/models` 不包含 `tencent/hy3:free`；`POST /v1/responses` 返回 `502 unknown provider for model tencent/hy3:free`，证明坏卡被 fail-closed 隔离而未转发上游。补充用临时复制 profile 按 remediation 新建正确 `openai-compatible` OpenRouter 卡片后，`/v1/models` 包含 `tencent/hy3:free`，`/v1/responses` 同模型返回 `HTTP 200` 且输出 `OK`。
- 结论：OpenRouter 当前问题属于历史错误账号类型导致的运行态注册链路错误。最终治理是“阻止新错卡 + 审计旧错卡 + 隔离旧错卡 + 用户删建为 openai-compatible”，不保留长期 legacy bridge。落位：`docs-linhay/spaces/20260708-openrouter-hy3-free-diagnosis/README.md`。

## 正式版 accounts-v1.sqlite 损坏恢复（紧急止血）

- **故障现象**：点击"删除账号"报 `DELETE ERROR: 后端未就绪`；重启后 sidecar 卡在"正在启动后端服务…"30 秒后超时，反复重启无效。

- **恢复操作**：
  1. `sqlite3 accounts-v1.sqlite ".dump" > /tmp/accounts_dump.sql`（dump 以 `ROLLBACK; -- due to errors` 结尾，需 `sed` 替换为 `COMMIT;`）
  2. `sqlite3 /tmp/accounts-v1-recovered.sqlite < /tmp/accounts_dump_fixed.sql`
  3. 完整性检查通过，行数：auth_file 3001、account_cards 3006、identities 1202、codex_keys 3 全保留；account_runtime_apply_state 2103（损坏页 903 条运行时缓存丢失，sidecar 重建）

## waitHealthy 子进程早退感知修复

- **问题**：`internal/sidecar/process_support.go` 的 `waitHealthy` 只在轮询间隔用 `time.Sleep`，不感知子进程是否已退出，导致 sidecar 闪退后 App 硬等 30 秒才报"健康检查超时"。
- **修复**：将 `time.Sleep(pollInterval)` 改为三路 `select`：`ctx.Done()` / `done`（进程退出）/ `time.After(pollInterval)`；同时在每次 HTTP 尝试前也先 select 检测。子进程退出时读取 `m.exitErr`，按有无错误分别返回 `"进程提前退出: <err>"` 或 `"进程提前退出 (exit 0)"`。
- **文件**：[`internal/sidecar/process_support.go`](file:///Users/linhey/Desktop/linhay-open-sources/GetTokens/internal/sidecar/process_support.go)
- **测试**：新增三个测试：非零退出立即返回、exit 0 立即返回、/healthz 200 正常路径；26/26 全绿，无回归。
- **效果**：sidecar 因 SQLite CORRUPT 等原因启动失败时，App 立即报 `"进程提前退出: <具体原因>"`，用户体验从 30 秒卡死变为秒级反馈。
