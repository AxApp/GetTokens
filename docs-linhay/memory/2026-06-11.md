## Route Guard token-window 失败 usage 统计修正
- 用户反馈 route guard Token 统计会先到约 80m 再降到约 1.2m，怀疑 fallback / fail back 流量先被加入 token 统计。
- 证据：只读查询 dev `usage-attribution-v1.sqlite`，最近 24h 失败请求 token 合计为 0；80m 级别来自成功 usage 汇总。但代码中 token-window SQL 直接 `SUM(total_tokens)`，未过滤 `failed`，若失败 attempt 携带 token 会误触发 guard。
- Space：`docs-linhay/spaces/20260611-route-guard-token-window-failed-usage/`。
- 修复：CLIProxyAPI fork `rateLimitTokenWindowStrategy` 只统计 `failed = 0` 的 usage attribution 事件；request-window 仍按事件数量统计。
- 回归：新增 `TestRateLimitEvaluatorTokenWindowIgnoresFailedUsageTokens`；focused 测试、`TestUsageAttributionPluginRefreshesRateLimitGuardAfterPersist` 与 `go test ./internal/gettokenshooks -count=1` 通过。
- 沉淀：本轮为既有 route guard 领域语义补窄，已写入 space 与 memory，不新增 skill / AGENTS 规则。

## Codex API key 可用但无法命中
- 用户在账号池标注 `公司 1`：账号卡显示可用，但 Codex 请求无法命中；同时追问为什么不能直接使用账号池、为什么还要投影。
- 现场证据：正式 sidecar 只读接口显示 `公司 1` 为 active `codex-api-key`、`runtime_apply_status=applied`，quota runtime 为 `success / blocked=false / plan_type=pro`；但 `/v0/management/accounts/:id/models` 返回空数组，sidecar 日志对 `gpt-5.4/gpt-5.5` 报 `auth_unavailable`。
- 根因：SQLite 账号池是事实源，但 sidecar 请求热路径仍依赖运行态 `AuthManager` / `ModelRegistry` 索引。无 watcher 的 account-store refresh 路径只刷新 config 快照，没有把 SQLite Codex API key 合成并注册进运行态索引；管理模型接口也没有对 `codex-api-key.models_json=[]` 回退默认 Codex 模型集。
- 修复：CLIProxyAPI fork 的 `refreshAccountStoreAuths()` 在无 watcher 时主动合成 account-store auth 并注册/移除运行态索引；`GetAccountModels` 对 active Codex API key 空模型列表回退默认 Codex Pro 模型集。
- 回归：新增 `TestServiceRefreshAccountStoreAuthsWithoutWatcherRegistersCodexAPIKeyModels` 与 `TestGetAccountModelsFallsBackToCodexDefaultsForAccountStoreAPIKey`；`go test ./sdk/cliproxy ./internal/api/handlers/management ./internal/watcher/synthesizer -count=1`、CLIProxyAPI fork `git diff --check` 通过。
- 沉淀：更新 `.agents/skills/gettokens-domain-engineering/SKILL.md` 和 `.agents/skills/gettokens-codex-account-list/SKILL.md`，明确“账号池是事实源，但运行态索引必须重建”和“Codex API key 空模型列表表示默认 Codex 模型集”。

## 账号卡刷新额度显示补漏
- 用户在账号池标注 `公司 1`：点击“刷新额度”后卡片可见信息没有变化。
- 现场证据：sidecar 管理接口 `quota-refresh` 实际会更新 `updated_at / last_evaluated_at`，`quota-status` 也有 `5H=40% / 7D=14%`；页面上用户看到的 `00:00-23:59 TOKENS 0 / 400M` 是 Route Guard，而非 quota window。
- 根因：前端初始化路径 `GetQuotaStatuses` 接收的是 sidecar runtime state 的 `snake_case` 字段，但 `buildQuotaDisplay` 只按 Wails `CodexQuotaResponse` 的 `camelCase` 读取，导致 quota window、reset、更新时间在账号卡模型层被丢弃或显示为空。
- 修复：`buildQuotaDisplay` 同时兼容 `camelCase` 与 `snake_case` quota runtime state；账号卡保持紧凑，只展示 quota window 与 reset，不额外显示 runtime refresh timestamp。
- 回归：新增 `frontend/src/features/accounts/tests/accountQuotaRuntime.test.mjs`；相关 `node --test`、`npm --prefix frontend run typecheck`、`npm --prefix frontend run build` 通过。

## Codex 浏览器预演候选池口径补漏
- 用户在 Codex 账号列表标注：下方请求顺序里 `公司 1` 等账号显示为“候选”，但高级诊断仍显示“未命中 / 候选 0 / 过滤 8”。
- 现场证据：当前 `localhost:34115` 页面无 Wails bindings，走 browser preview；列表候选与路由探测使用 `buildCodexRoutePolicyPreview()`，高级诊断 browser `runChannelExplain()` 分支却自行用 `orderedRows.filter(row.requestable)` 组装 candidates/filtered。
- 根因：同一页面的“请求顺序列表 / 路由探测 / 高级诊断预演”没有共享同一个候选池解释函数，浏览器预览状态下会出现同屏互相矛盾。
- 修复：新增 `buildCodexRoutePolicyExplainPreview()`，让 browser explain 复用 route policy preview 候选池，并统一输出过滤原因与项目候选池摘要。
- 回归：新增 `buildCodexRoutePolicyExplainPreview uses route policy preview as the candidate pool`；`node --test frontend/src/features/codex/codexAccountList.test.mjs`、`npm --prefix frontend run typecheck`、`npm --prefix frontend run build` 通过。

## manual-disabled 持久化边界修正
- 用户追问 `~/.config/gettokens-dev/channel-routing/config.json.runtimeStates` 是否是数据库，并指出账号池已有可用 `公司 1` 但 Codex 高级诊断仍未命中。
- 结论：`runtimeStates` 不是数据库，是 profile-local route guard runtime cache；账号禁用/启用事实必须以 SQLite account-store / management status 为准。
- 根因：上一期候选池同步把 `manual-disabled` 也作为持久 runtime source，导致启用账号后旧 JSON cache 仍能在 Wails explain 和 sidecar persisted guard 中覆盖 DB enabled 状态。
- 修复：Wails 保存 channel-routing store 时清理 legacy `runtimeStates.*.sources.manual-disabled`；`activeRuntimeBlockReason()` 不再把它作为硬阻塞；账号启用/禁用后触发同一清理路径。CLIProxyAPI fork 仍保留当前进程内存 `manual-disabled` 以保证禁用即时生效，但不再读取或写入共享 JSON 中的 `manual-disabled`。
- 回归：`go test ./internal/wailsapp -count=1`、`go test ./internal/sidecar -count=1`、CLIProxyAPI fork `go test ./internal/gettokenshooks ./sdk/cliproxy ./internal/api/handlers/management -count=1`、前端 `node --test frontend/src/features/accounts/tests/accountQuotaRuntime.test.mjs frontend/src/features/codex/codexAccountList.test.mjs`、`npm --prefix frontend run typecheck`、`npm --prefix frontend run build` 通过。
- 沉淀：更新 `.agents/skills/gettokens-domain-engineering/SKILL.md` 与 `.agents/skills/gettokens-codex-account-list/SKILL.md`，明确 `manual-disabled` 不再是持久 runtime fact，历史持久值必须忽略并清理。
