## 账号卡身份模型迁移

- 决策：GetTokens 本地产品模型不引入用户实体，只有账号卡；`account_key/account_id` 是账号卡唯一业务身份。
- 决策：账号登录、新增、导入、复制创建新账号卡；重新登录和编辑当前凭证更新原账号卡并保留原 ID。
- 决策：`auth-id/auth-index/provider/attribution_key/email/API key hash` 都是 runtime evidence，不允许作为 rate-limit 策略匹配键。

- 进展：已创建 space `docs-linhay/spaces/20260529-account-credential-sqlite-store/`，用于承接账号/凭证 SQLite 统一存储需求调研。

- 决策：GetTokens 不再管理账号事实源；账号相关改动全部放到 sidecar，GetTokens 只通过 sidecar management API 展示和发起账号操作。
- 决策：SQLite 迁移后的账号卡主 ID 应由 sidecar account store 分配为新的 `acct_*`，旧 `auth-file:*`、`codex-api-key:*`、`openai-compatible:*` 只进入 `account_runtime_identities` 做迁移、诊断和历史归因辅助。
- 决策：`account_key` 使用 UUID 分配，格式为 `acct_<uuid>`，每个账号卡唯一。
- 决策：敏感 entry 不写入 `secret_json` / secret store，明文存在 SQLite 对应类型表中，依靠 DB 文件权限、父目录权限和日志/debug export 脱敏保护。
- 决策：最终 SQLite schema 增加 `account_cards.revision`、`account_runtime_apply_state` 和 `account_migration_sources`，分别解决凭证更新驱动 sidecar runtime apply、当前进程使用旧凭证风险、旧源删除审计问题。
- 决策：迁移后直接修改 sidecar 侧账号事实源。OAuth finalize/relogin、token refresh、Codex API key 更新、OpenAI-compatible provider 更新都由 sidecar 写 SQLite 并刷新 runtime。
