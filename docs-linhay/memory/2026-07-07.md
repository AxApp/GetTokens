## 账号池刷新慢回归止血

- 根因：2026-06-08 已实现的账号页 runtime snapshot 快路径仍在 `useAccountsPageState`，但 `AccountsFeature` 后来新增了同名本地 `refreshAccountsRuntime`，header 实际调用本地函数并对全量账号执行 `refreshAccountQuotasBatch(accounts)`，导致 800+ 账号刷新重新退化为全量主动 quota refresh。
- 修复：`AccountsFeature` 改为消费 `useAccountsPageStateContext` 暴露的 `runtimeRefreshing/refreshAccountsRuntime`；hook 内部维护 busy guard，并继续用 `syncCodexQuotaStatuses(runtimeSyncAccounts, { replace: false })` 读取 sidecar runtime snapshot。菜单栏主动刷新从逐账号 `quota-refresh/:account` 改为一次 `quota-refresh-batch`。
- 沉淀：`gettokens-domain-engineering` 增补规则，禁止 `AccountsFeature` 定义 shadow 版全局 runtime 刷新；菜单栏多账号主动刷新必须使用 batch。
- 验证：前端账号测试全集 `node --test frontend/src/features/accounts/tests/*.test.mjs` 通过 `522 pass / 0 fail`；`npm --prefix frontend run typecheck`、`go test ./internal/wailsapp -count=1` 通过。

## 账号重复导入去重方案

- 新建 space：`docs-linhay/spaces/20260707-account-import-deduplication/`，已写入需求边界、证据门禁、技术方案、实现计划和测试计划。
- 测试包脱敏事实：`cpa-2026-07-06_23-33-06.zip` 含 875 个可解析 codex JSON；email 唯一数 691、重复组 16；account_id 唯一数 14，最大组 675；access_token/id_token 各 875 唯一；没有 refresh_token。结论是不能用文件名、原始 JSON、account_id 单独去重。
- 方案决策：导入去重必须在 `NormalizeAuthFileForSidecar` 之后计算 normalized credential identity，并由 sidecar/accountstore 批量创建边界强制执行；默认跳过强身份重复，弱身份冲突只提示，不做历史重复清理。
- 沉淀：`gettokens-domain-engineering` 增补规则，重复 auth-file 导入必须在 sidecar/accountstore 内按归一化凭据身份去重，batch-create 返回 created/skipped/error 摘要。

## 2000+ 账号滚动性能优化

- 调研结论：主流方案仍是虚拟列表/窗口化优先，React memo/useMemo 处理昂贵计算，CSS content-visibility 只作为辅助；GetTokens 已有分组窗口化，所以本轮优先修滚动期间的 CPU 热路径，而不是立即引入新虚拟列表依赖。
- 证据：2000 preview 账号无头浏览器检查仍保持 DOM 窗口化，首屏 `41` 张卡片、滚动后 `56` 张；卡顿候选落在 `AccountGroupSectionView` 每次 `renderMetrics` 滚动更新时重复扫 `group.accounts` 计算分组动作状态。
- 修复：新增 `resolveAccountGroupActionAvailability()` 一次扫描汇总分组选择/刷新/启停/删除可用性，视图用 `useMemo` 按 `group.accounts + selectedAccountIDSet` 缓存，滚动窗口变化不再反复扫 2000+ 分组。
- 沉淀：`gettokens-domain-engineering` 增补大账号列表规则，禁止 scroll-driven virtual window state 里做与滚动无关的 group-wide 动作聚合。

## 账号列表虚拟 spacer 过大修复

- 根因：`AccountGroupSectionView` 的虚拟窗口只测量视口和列数，full card 行高一直使用固定 `ACCOUNT_GROUP_FULL_ROW_ESTIMATE=448`；2000 preview 首屏 `plan:pro` 的 `bottomSpacer=234752` 正好等于 `524 * 448`，把内部滚动高度放大到接近 `299k px`。
- 修复：新增 `resolveAccountGroupMeasuredRowHeight()`，组件在已渲染卡片存在时用真实 row top 间距或卡片高度加 row gap 校准 `rowHeight`；固定估算只保留作首次渲染和测量失败兜底。
- 验收：`accounts-scale-browser-check.mjs` 增加 `measuredRowHeight` 与 `spacerEstimateRatio` 指标并默认要求比例 `<=1.35`。2000 preview `plan-full` 首屏从 `bottomSpacer=234752 / scrollHeight=298863` 降为 `bottomSpacer=163176 / scrollHeight=209919`，`measuredRowHeight=312`、`spacerEstimateRatio=1.00`。
- 矩阵：2000 账号 `plan-full / provider-full / status-full / plan-list` 均通过，所有虚拟组 `spacerEstimateRatio=1.00`，渲染卡片数仍低于 `220`。已通过账号前端测试全集 `527 pass / 0 fail` 与 `npm --prefix frontend run typecheck`。
- 沉淀：`gettokens-domain-engineering` 增补大账号列表规则，虚拟 spacer 必须优先使用实测渲染行距，验收脚本必须记录 spacer/实测行高比例。
