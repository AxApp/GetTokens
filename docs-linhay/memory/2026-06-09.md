## 账号池冷启动缓存首屏
- 用户反馈最新包多账号首次启动卡在账号池 skeleton，期望“先读缓存显示，更新后续跟上”；space：`docs-linhay/spaces/20260609-account-startup-cache/`。
- 排查结论：最近筛选改动会产生 filtered empty，不会产生 skeleton；卡屏根因是首屏等待 sidecar `ListAccounts()`，新安装包没有前端缓存，且正式 `accounts-v1.sqlite` 已出现 `database disk image is malformed (11)` 证据导致 `/v0/management/accounts` 连续 500。
- 实现：Wails `ListCachedAccounts` 在 sidecar ready 前只读 account-store SQLite 并返回脱敏账号卡；前端挂载即读 SQLite/localStorage 快照但不把它当实时完成态，`ListAccounts()` 成功后覆盖；实时失败且已有快照时停止无限重试。
- sidecar 修复：management `/accounts` 在 credential attach 失败时降级返回 `degraded=true` 的 card-only 列表；runtime 合成路径仍严格读取，避免缺凭证账号参与路由。
- 安全边界：账号列表快照不保存 `apiKey/apiKeys`、headers、cookie、cURL scripts、`modelFetchApiKey`、`rawAuthFile` 等敏感字段。正式库损坏恢复另行处理，本轮不改正式数据。
- 验证：Wails snapshot tests、sidecar accountstore/management/synthesizer tests、frontend cache/snapshot/filter tests、`typecheck`、`build`、`./scripts/wails-cli.sh build` 均通过；规则沉淀到 `.agents/skills/gettokens-domain-engineering/SKILL.md`，不升级 `AGENTS.md`。
- 追加正式环境恢复：用户授权后，对 `/Users/linhey/.config/gettokens/accounts-v1.sqlite` 做在线备份到 `/Users/linhey/.config/gettokens/recovery-20260609-181342/`，确认正式 `/v0/management/accounts` 500 的直接原因是 active auth-file card 缺失 credential（`sql: no rows in result set`）。修复后 `integrity_check=ok`，三类 active card orphan 均为 0，正式接口恢复 `200 OK` 并返回 `226` 个账号。
- 残留风险：当前干净正式库 active card 为 `226`，低于用户预期的 1000+；旧 malformed 库只能 dump 出与当前库一致的可读 rows，坏页里的账号无法用当前 sqlite shell 证明可恢复。后续找回更多账号需要原始导入包、外部备份或专门 SQLite page recovery。
