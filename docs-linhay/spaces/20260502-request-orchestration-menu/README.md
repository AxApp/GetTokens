# 2026-05-02 Request Orchestration Menu

## 背景
本轮方向已从“账号池页面改造”调整为“新增一个独立菜单承载请求编排”。需求核心不再是账号池信息架构，而是给请求路由、provider 激活、编排策略和相关控制入口一个独立工作区，避免继续塞进账号池语义里。

当前仓库里与请求分发相关的能力分散在：

- 账号轮动与 provider/workspace 入口
- 状态页中的 relay routing 配置
- sidecar 现有 `round-robin / fill-first / session-affinity`
- 独立代理池页面与既有账号级 `proxy-url`

这轮最新收敛后，页面心智不再是自由画布，而是一个**固定流程配置页**，直接按稳定链路表达请求从入口进入、落到哪个账号组、当前账号走什么出口，以及最后如何测试。

## 目标
为“请求编排”建立一轮独立空间，承接新菜单的需求边界、固定流程配置结构、实现计划、截图和验收记录。

本轮首先收敛以下问题：

- 请求编排是否作为独立一级菜单出现
- 页面是否应收敛为固定流程配置，而不是引入自由画布
- 哪些能力属于 APP 层编排，哪些只是 sidecar 已有状态透出
- `请求入口 -> 账号组与代理 -> 账号出口 -> 结果与测试` 四段分别展示什么、能编辑什么
- 多组固定流程如何切换、自定义，并保持每组各自的入口、账号组、账号出口和测试状态
- 每个账号需要声明支持哪些 CLI，以及如何把入口模型映射到该账号真实可用模型
- provider lock / 激活唯一 provider 应作为哪一类节点动作出现
- 实现完成后需要哪些自动化验证与桌面验收

## 范围
- 新菜单“请求编排”的信息架构、入口定义与页面边界
- 与请求编排直接相关的前端页面、feature、状态组织和交互闭环
- 与请求编排页面直接相关的 Wails 接口编排
- 本轮请求编排需求的计划文档、截图和 debate 记录

若本轮实现涉及以下内容，也纳入范围：

- relay routing 配置编辑入口重组
- provider 激活 / 唯一 provider 编排入口
- 账号组、账号列表和账号级代理池开关的可视化编排
- 账号级代理池启用状态、当前出口和代理模式展示
- 账号级 `支持的 CLI` 配置
- 账号级 `模型映射 / alias` 配置与可视化摘要
- 出口视角的链路预览与结果摘要
- 请求分发相关的页面文案、空状态和工作区拆分
- 多个请求编排流程组的新增、复制、重命名、删除、切换、保存与恢复
- 为请求编排页面补充或调整的前端/Go 测试

## 非目标
- 不把该需求继续挂在账号池菜单下实现
- 不在本轮默认修改 CLIProxyAPI 原生策略枚举
- 不把它做成自由拖拽、缩放、连线的图编辑器
- 不把代理池节点 CRUD 直接搬进本页；代理池仍是独立页面
- 不在 README 中直接承诺最终视觉稿；设计稿另行落到本 space 根目录单一 HTML 文件
- 不在没有明确验收标准前，顺手重做全部账号池或 sidecar 管理体系

## 验收标准
1. “请求编排”作为独立菜单的需求边界、目标与非目标在本 README 中可追踪。
2. 页面主结构明确采用固定流程配置，且四个固定阶段均有稳定职责定义。
3. 请求入口固定为 `codex` 和 `claude code` 两个选项，用户点击即可选中当前入口。
4. 页面支持多组固定流程；每个流程组都包含完整的 `01 请求入口 -> 02 账号组与代理 -> 03 账号出口 -> 04 结果与测试`，并独立保存当前入口、账号组、账号出口覆盖、测试状态和最后操作摘要。
5. 账号组阶段以账号列表为主要操作面，单个账号可独立配置是否启用代理池。
6. 用户可以自定义流程组：新增空白自定义组、复制当前组、重命名当前组、删除非唯一当前组。
7. 后续实现计划统一落到 `plans/`，不再继续借用账号池相关 space。
8. 若本轮涉及视觉或交互调整，验收截图统一落到本 space 的 `screenshots/`。
9. 若实现过程中存在方案争议，讨论记录统一落到本 space 的 `debate/`。
10. 当代码改造开始后，自动化验证、Wails 验收结论和收尾说明可回链到本 space。

## 当前需求

### 页面定位

`请求编排` 是一个新的一级菜单，职责是把“请求如何被组织和发出”收口到一个独立工作台中。

它不是：

- 账号资产管理页
- provider 新增/编辑页
- 代理池管理页
- sidecar 原生策略枚举展示页

它是：

- 请求链路编排页
- 当前生效路径预览页
- APP 层编排动作的执行入口

### 页面主模型：路径优先的单面板编辑

页面不再把一组编排拆成四张并列重卡。展开流程组后，先展示一条完整路径摘要，再在下方用三个决策区完成编辑：

1. `路径摘要`：一行展示 `入口 -> 账号组 -> 账号 / 出口 -> 测试`，负责回答“这组请求现在会怎么走”。
2. `1. 请求入口`：只列出 `codex / claude code` 两个 CLI，点击即切换入口。
3. `2. 账号`：先选账号组，再选账号；单个账号的代理池启用/禁用跟着当前账号操作。
4. `3. 出口与测试`：当前账号未启用代理池时只显示 `直连`；启用代理池后才显示代理出口列表；测试按钮在同一块内完成。

顶部不再展示 `状态 / 账号池 / 请求编排 / 代理池 / 设置` 这类应用主导航，也不保留独立的流程组工具 `section`。页面结构收敛为 `header + main`，`header` 只放品牌标识、流程组操作、恢复和应用；页面不再保留底部结果坞，最终路径、应用状态和测试结果只在展开组内表达。

交互补充：

- 页面不提供自由画布平移、节点拖动或端口拖线。
- 页面不采用三栏布局，也不采用纵向长流程；核心工作区固定为路径摘要 + 单面板编辑。
- 设计稿不展示应用级主导航，避免 `01 状态 / 02 账号池 / 03 请求编排 / 04 代理池 / 05 设置` 抢占编排焦点。
- `/html/body/div[1]` 下面不再保留独立 `section`；直接子节点只允许是顶栏 `header` 和主工作区 `main`。
- `/html/body/div[1]/main` 内的一个流程组头 + 展开后的路径摘要和决策区，才是一组完整编排。
- `/html/body/div[1]/main/div/section[n]/div` 是某个流程组展开后的完整组内设计容器，必须包含路径摘要和三个决策区，不允许只是空容器。
- 多组默认全部折叠，只展示组头摘要；点击某个组头后只展开该组，其他组保持或回到折叠状态。
- 流程组的新增、复制、重命名、删除集中在顶部流程组栏右侧；复制、重命名、删除需要先展开一个组。
- 决策区只保留必要操作，重复的“当前配置”KV 不再展示；路径摘要负责承载最终结果。
- `01 请求入口` 只展示 CLI 入口和应用状态，不显示模型；模型映射只作为账号兼容性与最终出站判断，不在入口阶段抢占配置语义。
- 不再额外展示底部 path / metrics / console 视图，避免和第 04 卡重复。
- 路径摘要使用横向链路样式，按 `入口 -> 账号组 -> 账号 / 出口 -> 测试` 表达最终生效路径。
- 当前组编辑后必须明确显示 `未应用更改`，点击 `应用当前组` 后才显示 `已应用当前组`。
- 入口切换后，账号组和账号兼容性即时刷新。
- `02 账号组与代理` 必须显式受 `01 请求入口` 驱动：组 ready 数、账号可参与状态、灰态原因和当前账号都要根据当前入口重算。
- 账号组切换后，当前账号和结果区即时刷新。
- 当前账号的出口选择通过点击固定出口目标完成，不引入拖拽状态机。

### 多流程组

请求编排页面需要支持多组固定流程。每个流程组都是一条完整的 `01 -> 02 -> 03 -> 04`，不是第二阶段的账号组，也不是单条流程的配置快照。

每个流程组至少独立持有：

- 当前 CLI / 请求入口
- 当前选中的账号组
- 当前编辑账号
- 每个账号的出口覆盖关系
- 最近一次操作摘要
- 最近一次测试状态、测试日志和路径快照

交互要求：

- 用户可以在主工作区通过流程组头展开/收起流程组；内置只保留 `默认组` 和 `自定义组`，不再提供 `生产编排 / Claude 备用 / 实验编排` 这类场景预设。
- 用户可以新建一组自定义流程，新组默认包含完整 01-04，且可继续编辑入口、账号组、账号出口和测试状态。
- 用户可以复制当前流程组，复制结果保留当前组的入口、账号组、当前账号和账号出口覆盖，但测试状态回到未测试。
- 用户可以重命名当前流程组。
- 用户可以删除当前流程组；当只剩一组时不允许继续删除。
- 切换流程组前，当前页面的临时选择需要写回当前流程组。
- 切换到另一个流程组后，路径摘要、决策区选择和测试区都应恢复为该流程组自己的状态。
- 在某个流程组内修改账号出口，不应污染其他流程组的出口关系。
- 流程组只管理编排配置，不直接创建或删除账号资产、provider 资产或代理资产。

### 阶段 1：请求入口

这一段负责表达“什么请求会进入这条固定链路”。

入口固定为两个选项列表：

- `codex`
- `claude code`

这一段的动作边界：

- 允许点击选中当前入口
- 入口只影响后续账号兼容性与模型映射判断；入口卡自身不显示模型字段
- 不在这一段直接管理账号资产

### 阶段 2：账号组与代理

这一段负责表达“请求进入后，会落到哪一组账号，以及组内每个账号是否允许使用代理池”。

第二阶段不是静态账号池列表，它必须根据第一阶段入口即时派生：

- 当前入口写在第二阶段列表顶部
- 账号组展示“当前入口下可参与账号数”
- 账号展示“可参与 / 不可参与”以及灰态原因
- 切换入口后，若当前账号不再兼容，应自动选择当前入口下的第一个可参与账号；当前组无可参与账号时，再切到第一个可参与组

第二阶段仍保留账号组切换，但主要操作面必须是账号列表：

- `Codex 组`
- `OpenAI-Compatible Provider 组`
- 后续如有需要再扩更多组

每个组卡至少展示：

- 组名
- 当前是否参与
- 组内可用对象数量
- 当前是否被锁定为唯一活跃组
- 排除原因（若被禁用或被其他编排模式排除）

账号列表至少展示：

- 账号名 / provider / baseUrl
- 当前入口 CLI 与模型映射状态
- 该账号是否启用代理池
- 当前出口摘要
- 选择账号、启用/关闭代理池、禁用/启用账号、移出组

这一段的主动作：

- `激活为唯一提供组`
- `恢复普通参与`
- 查看组内对象详情
- 对单个账号启用或关闭代理池

说明：

- 如果用户激活唯一 provider，本质上是 APP 层编排动作，不要求 sidecar 新增原生 `strategy`
- 页面需要明确这是“唯一组/唯一 provider 激活”，不是 sidecar 原生第三种轮动策略
- 单个账号关闭代理池时，最终出口固定为 `direct`；该账号之前选过的代理可以保留在 profile route 中，重新启用代理池后恢复。

### 阶段 3：账号出口 / 代理池

这一段负责表达“当前编辑账号是否走代理，以及走哪种出口”。

这一段的核心对象是账号级出口语义，而不是图节点本身。

代理模式对齐现有规格，固定为：

- `inherit`
- `direct`
- `custom`

语义对齐 `docs-linhay/dev/20260429-gettokens-proxy-spec-v01.md`：

- `inherit`：不写显式 `proxy-url`
- `direct`：显式直连
- `custom`：携带明确 `proxyUrl`

这一段建议展示为“当前账号摘要 + 固定出口目标列表”：

- 当前编辑账号名称
- 当前账号是否兼容入口
- 当前出口
- 可选出口列表
- 代理摘要
- 模型映射摘要

这一段建议支持的动作：

- 切换账号代理模式
- 选择直连或具体代理
- 查看账号支持的 CLI 集合
- 查看账号模型映射
- 快速跳转到代理池页面查看或维护代理节点

这一段不负责：

- 在本页直接做代理池节点新增、删除、导入

模型映射语义先按“入口模型 -> 账号真实模型”理解，尽量复用仓库现有 `models[].name / models[].alias` 表达，不单独发明新的映射字段名。

### 阶段 4：结果与测试

这一段负责表达“固定流程下最终请求会从什么出口发出，以及测试结果如何”。

上方链路区必须使用垂直时间轴样式展示：

- `01 请求入口`
- `02 账号组`
- `03 账号出口`
- `04 测试`

下方测试配置至少需要展示：

- 当前出口类型
  - 直连
  - 代理出口
  - 继承环境
- 最终出口摘要
  - provider / baseUrl
  - proxy mode
  - proxy url 摘要（如存在）
- 当前参与出口的对象数量

这一段更偏结果预览，而不是设置页：

- 用于确认上一段配置后的最终生效路径
- 用于帮助用户判断配置是否符合预期
- 用于从固定流程末端一键测试

### 页面区块补充

当前版本不再增加页面底部收口区；所有结果预览和测试入口都收敛到第 `04 结果与测试` 卡片中。

### 管理交互约定

#### 账号组如何添加、移出、禁用、启用账号

账号组节点负责“账号是否参与当前编排”，不负责删除账号资产本体：

- `从账号池加入`：从账号池中选择已有账号加入当前账号组。
- `移出当前组`：只把账号从当前编排组移出，不删除账号池里的账号文件、API key 或 provider 资产。
- `禁用账号`：账号仍留在组内和顺序中，但不参与当前有效出口集合。
- `启用账号`：恢复该账号参与编排，仍需同时满足当前入口 CLI 与模型映射。

实现时，禁用/启用应优先复用统一账号禁用入口；移出组属于 APP 层编排 overlay。

#### 单个账号如何和代理关联

账号与代理的关联发生在固定出口列表中：

- 选择账号后，点击 `直连` 或某个代理 tile，即可把该账号关联到该出口。
- `直连` 是系统出口，不可删除。
- 代理被禁用时，相关账号不会进入最终有效出口集合；删除代理时，已关联账号回落为 `直连`。

#### 代理组如何添加、删除、搜索、禁用、启用代理

代理池节点负责代理目标的选择与参与状态，不承载复杂代理资产管理：

- `搜索`：在代理池节点内按代理名称、区域、备注过滤 tile。
- `+ 代理`：添加一个代理目标占位，后续可跳转代理池页面补齐真实配置。
- `禁用代理`：代理目标仍保留在列表中，但不再作为可用出口。
- `启用代理`：恢复该代理作为可用出口。
- `删除代理`：从当前编排代理池移除该代理目标；若有账号关联该代理，账号自动回落 `直连`。

代理节点 CRUD 的深度编辑仍应回到独立代理池页面；请求编排页只做“参与当前链路”的轻量编排。

## 领域边界

### 1. APP 层编排优先

本轮新增的“唯一 provider / 唯一账号组”语义，默认先按 APP 层编排实现，不要求 CLIProxyAPI 增加新的原生 `routing.strategy`。

### 2. 账号组与账号资产分层

页面第二类节点展示“账号组”，第三类节点展示“账号级代理 / 代理池挂接”，不要把“选择组”和“编辑单个账号代理”混成一层。

### 3. 账号兼容性必须显式可见

当入口 CLI 或入口模型变化时，页面需要能够明确表达：

- 哪些账号支持当前 CLI
- 哪些账号虽然在组内，但没有对应模型映射
- 哪些账号因此被排除在本次有效出口之外

### 4. 代理池继续独立

请求编排页面只消费代理结果和代理模式，不承载代理池本体管理；代理池仍保留独立一级页面。

### 5. 页面必须表达链路，而不是只表达字段堆叠

用户进入本页后，第一感知应是“请求怎么走”，不是“我在编辑一堆 YAML/JSON 配置”；但这种表达通过固定流程和结果预览完成，不依赖自由画布。

## BDD 场景

### 场景 1：进入请求编排页时看到完整固定流程

- Given 用户进入应用主界面
- When 用户点击一级菜单 `请求编排`
- Then 页面按固定流程展示：
  - `请求入口`
  - `账号组与代理`
  - `账号出口`
  - `结果与测试`
- And 用户无需展开调试信息就能理解当前请求链路

### 场景 2：激活唯一 provider 组

- Given 页面已展示多个可参与请求的账号组
- When 用户在 `账号组` 节点中选择某个 provider 组并点击“激活为唯一提供组”
- Then 该组显示为唯一活跃组
- And 其他组显示为被排除
- And `出口` 节点的结果预览同步更新

### 场景 3：按账号启用代理池后切换出口

- Given 用户已进入 `账号组与代理` 阶段
- And 当前组内存在多个账号
- When 用户在某个账号行点击 `启用代理池`
- Then 该账号行展示代理池已启用
- When 用户在 `账号出口 / 代理池` 阶段为该账号选择一个代理出口
- Then 该账号行展示新的出口摘要
- And `结果与测试` 同步反映该变化

### 场景 4：账号显式直连覆盖默认代理

- Given 当前账号已启用代理池并选择过代理出口
- When 用户在账号行点击 `关闭代理池`
- Then 该账号最终出口固定回 `direct`
- And 该账号行展示代理池关闭
- And 出口预览中明确显示该账号走直连

### 场景 5：没有可用组时给出空状态

- Given 当前没有任何可参与请求的账号组
- When 用户进入 `请求编排`
- Then 页面展示明确空状态
- And 空状态说明缺的是哪一层：
  - 没有账号组
  - 没有可用账号
  - 没有可选出口

### 场景 6：按账号声明支持的 CLI

- Given 用户已进入 `账号出口 / 代理池` 阶段
- And 某个账号当前只支持 `codex`
- When 用户为该账号补充支持 `claude`
- Then 该账号卡片应显示新的 CLI 支持集合
- And 当入口切换到 `claude` 时，该账号不再因 CLI 不兼容被排除

### 场景 7：按账号配置模型映射

- Given 当前入口模型为 `gpt-5.5`
- And 某个账号存在 `models[].name / models[].alias` 配置
- When 用户把该账号的入口模型映射调整为 `gpt-5.5 -> gpt-5.4-mini`
- Then 账号卡片显示最新映射摘要
- And `出口` 节点展示的最终目标模型同步更新

### 场景 8：入口模型无映射时标记账号不可用

- Given 当前入口 CLI 与账号兼容
- And 该账号没有当前入口模型的映射关系
- When 页面刷新当前编排结果
- Then 该账号应被标记为“缺少模型映射”
- And `出口` 节点不把该账号计入可用出口对象

### 场景 9：恢复普通编排

- Given 用户此前启用了唯一 provider 组
- When 用户点击“恢复默认编排”
- Then 页面退出唯一组模式
- And 相关组的参与状态恢复到默认编排结果
- And 出口预览同步恢复

## 开放问题

1. 第一阶段的“账号组”是否固定只展示 `Codex` 与 `OpenAI-Compatible` 两组，还是允许更细的 provider 组展开？
2. 第三段“账号代理”里的 `custom` 模式，是直接选现有代理池节点，还是先只允许输入 `proxyUrl`？
3. “请求入口”是否需要区分不同客户端来源，例如本地 Codex 与 Relay API 调用？
4. `支持的 CLI` 是多选集合，还是区分“主要 CLI + 兼容 CLI”两层语义？
5. 模型映射是全局按账号维护，还是需要细化到“按 CLI 维护不同映射表”？
6. 入口模型映射是否严格复用现有 `models[].name / models[].alias`，还是需要额外的“入口模型别名”层？
7. “出口”是否需要展示真实探测能力，还是第一阶段只做配置结果预览？
