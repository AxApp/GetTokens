## 账号池分组删除兼容旧 sidecar 404
- 用户反馈正式版账号池点击“移除本组”后提示 `SIDECAR 请求失败 (404): 404 NOT FOUND`，组和账号都没有消失。
- 根因定位：分组删除和 selected bulk delete 都统一走 `DeleteAccountsBatch -> POST /v0/management/accounts/batch-delete`；该路由是 2026-06-09 新增的，正式版 bundle 若仍携带旧 sidecar，就会在批量删除入口直接 404。
- 修复：`internal/wailsapp/accounts.go` 的 `DeleteAccountsBatch` 遇到 sidecar 404 时，自动降级为逐账号 `DELETE /v0/management/accounts/:id`，继续返回批量成功/失败摘要，并保持删除成功后的 cache prune / 列表刷新语义。
- 回归：新增 `TestDeleteAccountsBatchFallsBackToSingleDeleteWhenBatchRouteMissing`，验证请求顺序、成功/失败汇总和 auth metadata cache 清理；`go test ./internal/wailsapp -run 'TestDeleteAccountsBatchUsesBatchManagementAPI|TestDeleteAccountsBatchFallsBackToSingleDeleteWhenBatchRouteMissing' -count=1` 通过。
- 沉淀：更新 `.agents/skills/gettokens-domain-engineering/SKILL.md`，约束“新增 sidecar management endpoint 落在既有热路径时，Wails/root 必须考虑旧 sidecar 404 的兼容降级，而不是把缺路由直接暴露给 UI”。

## macOS 26.x 在线更新兼容降级
- 用户通过正式版 app 内在线更新后，系统弹出“GetTokens.app 已损坏，无法打开”，触发场景是 Sparkle 原生更新入口，不是手动下载 DMG。
- 证据链：正式版 `v1.2.1` 的 DMG、`codesign`、`spctl`、`stapler`、`syspolicy_check distribution` 都通过；但 GUI 启动日志出现 `ASP: Security policy would not allow process`。
- 对照实验显示：保留 `com.apple.provenance` 的 app 副本无法稳定启动；去掉 `com.apple.provenance` / `com.apple.macl` 的副本可以启动，说明更像 macOS `26.x` 对 Sparkle 更新后 app 的 provenance/runtime policy 拦截。

- 回归测试：新增 `internal/wailsapp/app_test.go`，覆盖 Darwin 版本解析、原生更新 UI 启用门槛和 Wails 暴露的更新能力开关。

## Codex 账号列表与账号池统一 auth-file provider 识别
- 用户反馈线上 `Codex -> 账号列表` 为空，并明确要求 Codex 账号列表与账号池不能再各走一套识别逻辑。
- 根因定位：`internal/accounts/account_records.go` 的 `buildUnifiedAuthFileAccountRecord()` 对 account-store 返回的 auth-file 只信任 `provider/auth_type`；当 store 元数据仍是 `unknown` 时，`ListAccounts` 产出的统一账号记录仍是 `provider=unknown`。账号池 `ListAuthFiles` 已会从 `auth_json` 反推 `codex`，于是出现“账号池能认出，Codex 列表认不出”的分叉。
- 修复：把 auth-file provider 推断下沉到统一账号映射层；若 unified auth-file 的 store provider 为 `unknown`，则从 `auth_json` 统一推断 provider，并沿 `ListAccounts` 返回给所有消费方。
- 回归：新增 `TestBuildUnifiedAuthFileAccountRecordInfersCodexProviderFromAuthJSONWhenStoreMetadataUnknown` 与 `TestListAccountsInfersCodexAuthFileProviderFromUnifiedAuthJSON`；相关 `internal/accounts` / `internal/wailsapp` 定向测试通过。
- 稳定决策：涉及 Codex 账号列表、账号池、路由候选等共享账号面时，provider/type 推断必须放在统一账号映射层，不在单个页面各自补洞。

## 正式版 1.2.2 live sessions 显示已删除账号
- 用户反馈本地最新正式版 `Codex -> 运行会话` 显示 `jasonnike26-8ct1mmvx@yahoo.com`，但该账号不在账号池中。
- 只读核验：`/Applications/GetTokens.app` 正在运行 `1.2.2`，sidecar profile 是正式 `/Users/linhey/.config/gettokens/config.yaml`；`GET /v0/management/accounts` 对该邮箱匹配数为 `0`，但 `GET /v0/management/gettokens/live-sessions` 仍返回 `authLabel=jasonnike26-8ct1mmvx@yahoo.com` / `authID=jasonnike26-8ct1mmvx-auth-2.json`。
- 根因：安装版 bundle 内置 sidecar 的 `cli-proxy-api.meta.json` 为主仓 tag `539567d`，二进制缺少 `accountCoarseAvailable`、`RuntimeAccountProjection`、`PruneCodexLiveSessionsForAccount` 特征；当前开发构建 `build/bin/cli-proxy-api` 为 sidecar commit `2acd6ec0` 且已有投影字段。也就是说修复在开发构建里，未进入当前安装的正式版 sidecar。
- 处理边界：未替换、重启或 kill `/Applications/GetTokens.app` 正式版；该问题需要重新打包正式版并验 bundled sidecar metadata，而不是在用户机器上手动替换 sidecar。
- 沉淀：更新 `.agents/skills/gettokens-release-governance/SKILL.md`，把官方 DMG 验收扩展为必须校验 `cli-proxy-api.meta.json` 的 sidecar commit 与 reference commit 一致；若发布修复依赖 sidecar 字段/endpoint，还必须验证对应二进制特征或只读 management API 字段存在。
- 流程修复：Release workflow 不再用 `git -C docs-linhay/references/CLIProxyAPI rev-parse HEAD` 推断 sidecar commit，因为 CI 未 checkout gitlink 时会误读主仓 HEAD。现在改为从 `git ls-tree HEAD docs-linhay/references/CLIProxyAPI` 读取 gitlink commit，并把它同时写入 `CLI_PROXY_COMMIT` 与 `CLI_PROXY_SOURCE_REF`；`ensure-sidecar.sh` / `build-sidecar.sh` 在 source 目录缺失时按指定 ref fetch，而不是 fallback clone 旧远端分支。若 sidecar 提交未推送到远端，CI 会直接失败。
