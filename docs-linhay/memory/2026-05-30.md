- 正式 App 迁移页报错根因定位为 sidecar `accountstore.Open` 未给 modernc SQLite 连接配置 `busy_timeout`。启动期 management API 与 watcher/synthesizer 并发访问 `accounts-v1.sqlite` 时，`EnsureSchema` 写入 metadata 遇到短暂写锁会直接返回 `SQLITE_BUSY`，表现为 `ensure account store metadata: database is locked (5)`。
- 已在 `docs-linhay/references/CLIProxyAPI` 的 `gettokens/sidecar` 分支提交修复：`e6655916 fix: wait for account store sqlite locks`。修复内容是使用 `file:` DSN 为 account store 每个连接设置 `_pragma=busy_timeout(5000)` 与 `_pragma=foreign_keys(1)`，并新增并发写锁回归测试。
- 验证通过：`go test ./internal/gettokens/accountstore -run TestStoreEnsureSchemaWaitsForConcurrentSQLiteWriter -count=1`、`go test ./internal/gettokens/accountstore`、`go test ./internal/api/handlers/management ./internal/watcher/synthesizer ./internal/gettokens/accountstore`、`go test ./...`。
- 已重建父仓 `build/bin/cli-proxy-api`，meta 指向 `e6655916:clean`，版本输出为 `v7.1.16-92-ge6655916`。
- 按用户要求不停止正式 App/sidecar。正式环境只读在线复制到 `~/.config/gettokens-dev` 与 `~/.config/gettokens-dev-data`，dev 配置隔离为端口 `18317`、`auth-dir: ~/.config/gettokens-dev`、`account-store-db: ~/.config/gettokens-dev/accounts-v1.sqlite`。

## 账号凭证 SQLite token refresh 写回

- 用户确认迁移后 `auth_file_accounts.auth_json` 必须承载完整 auth-file JSON，不能再依赖旧 `codex-*.json`。凭证 refresh 会更新，因此 sidecar 需要在 refresh 成功后把新 token payload 写回 SQLite。
- 根因：迁移后 runtime auth 从 SQLite 合成，但 Codex 自动 refresh 成功后走 `coreauth.Manager.Update()` 的通用持久化入口；该入口原本仍是文件 store 语义，导致迁移后的 auth-file 账号没有稳定写回 `auth_file_accounts.auth_json`。
- 修复边界：sidecar 新增 account-store token store 包装层。`Auth.AccountKey=acct_*` 且账号为 `auth-file` 时，`Manager.Update()` 持久化会更新原账号的 `auth_file_accounts.auth_json`，保留 `account_key`，不新建账号卡，不写旧 auth-file；account store 内的非 `auth-file` 账号也不会 fallback 到旧文件 store。
- 运行时 token refresh 是当前 runtime 生成的新 credential snapshot，只更新类型表和 `updated_at_unix_ms`，不递增 `account_cards.revision`，避免重新排队 runtime apply；management API 发起的凭证/配置编辑仍必须 bump revision 并触发 apply。
- 已补测试覆盖 `UpdateAuthFileCredential` 不改 revision、`coreauth.Manager.Update()` 真实入口更新 SQLite、非 account-store auth 才 fallback、account-store 非 auth-file 不 fallback、refresh payload 缺套餐时保留已有 `plan_type`。

## 账号池导入账号写入 SQLite

- 用户发现账号池“导入账号”仍会创建 `codex-*.json` 文件。排查确认前端 `submitAccountImport` 对 auth-file payload 仍调用 Wails `UploadAuthFiles`，而该方法 POST 旧 sidecar `/v0/management/auth-files` multipart 上传端点；sidecar handler 会 `os.WriteFile` 到 `auth-dir`，所以这条链路没有进入 SQLite。
- 修复：公开 `UploadAuthFiles` 改为解码/规范化 auth JSON 后调用 `/v0/management/accounts` 创建 `kind=auth-file` 账号，写入 `auth_file_accounts.auth_json`。旧 `/auth-files` 上传逻辑拆成私有 `uploadLegacyAuthFiles`，仅供迁移前文件替换和 OAuth 文件回填兼容流程使用。
- 验证：`go test ./internal/wailsapp -run 'TestUploadAuthFilesConvertsChatGPTSessionToCPA|TestUpdateAuthFilePriorityPreservesDisabledStatus|TestUniqueAuthFileUploadName|TestApplyDeepLinkImportAuthFile|TestFinalizeCodexOAuth' -count=1`、`go test ./internal/wailsapp -count=1`、`go test ./internal/accounts -count=1`。
