## Usage Desk 会话下钻调研

- 新建 `docs-linhay/spaces/20260519-usage-session-drilldown/`，调研 `UsageDetailTable` 用量明细、图表选中和 Codex session 列表之间的关系。
- 结论：当前表格点击只按 `timeLabel` 同步图表选中点，不会打开会话；`projected` 本地用量链路后端 SQLite 已保存 `rollout_path`，但 DTO 当前没有把 session id 暴露到前端。
- 可行方案：首版在 `LocalProjectedUsageDetail` 透出 `sessionID/rolloutPath`，前端按点击的日/分钟 bucket 聚合并展示相关会话列表，每个 session row 标注当前 bucket 内请求数、输入、缓存、输出和总 token；`observed` sidecar 真实请求量因缺少稳定 session id，暂不做本地会话下钻。
- 已按用户确认收紧为“本期只做本地模式”并完成实现：后端 `LocalProjectedUsageDetail.sessionID` 透出 `rollout_path`，前端 projected snapshot 构造日级/分钟级 session usage bucket，Usage Desk projected 表格下方展示 `LOCAL SESSIONS` 下钻面板；observed 不展示本地会话。
- 验证通过：`go test ./internal/wailsapp`、`go test ./...`、`node --test frontend/src/features/accounts/tests/usageDesk.test.mjs`、`npm --prefix frontend run test:unit -- src/features/accounts/tests/usageDesk.test.mjs`、`npm --prefix frontend run typecheck`、`npm --prefix frontend run build`；浏览器预览截图归档到 `docs-linhay/spaces/20260519-usage-session-drilldown/screenshots/20260519/usage-desk/`。

## Codex WebSocket 路由策略

- 用户指出下游已经发起 WebSocket 时，GetTokens/CLIProxyAPI 不应因为 `codex-api-key` 没有显式 `websockets=true` 就跳过高优先级代理账号；正确语义应是按下游协议尝试当前候选账号，只有显式 `websockets=false` 才禁用。
- 排查确认当前真实请求链路为 `Codex CLI -> 127.0.0.1:8317 -> auth-2.json OAuth -> wss://chatgpt.com/backend-api/codex/responses`，原因是 `AuthDataAllowsWebsockets` 只让 Codex auth-file 默认支持 WebSocket，而 `codex-api-key` 默认被判为不支持，导致 `preferCodexWebsocketAuths` 在下游 WebSocket 场景过滤掉最高优先级 `cpa.host.dxy` 代理账号。
- 已在 `docs-linhay/references/CLIProxyAPI` 修正策略：Codex provider 下账号默认跟随下游 WebSocket，显式 `websockets=false` 才禁用；更新选择器与 scheduler 测试，确认 `codex-api-key` 默认可参与 WebSocket 且保留优先级顺序。
- 验证通过：`go test ./sdk/cliproxy/auth`、`go test ./sdk/api/handlers/openai ./internal/runtime/executor`。注意当前运行中的 `/Applications/GetTokens.app` sidecar 仍是旧二进制，需重新构建/替换后实机路由才会生效。

## Usage Codex 5-18 用量调查

- 调查结论：`usage-codex` 里 2026-05-18 显示约 `16.13 亿` 的来源是 `projected / 本地投影用量`，不是 sidecar `observed / 真实请求量`。按北京时间自然日重算 `session_usage_minutes_v2`，`input + output = 1,612,779,530`，其中 `cached_input_tokens = 1,496,475,008`，约占 input 的 `93.06%`。
- 对照 sidecar prod attribution ledger，同日 `observed total_tokens = 276,809,493`；若按非缓存口径粗算，本地投影约 `116,304,522`，sidecar observed 约 `17,012,501`。因此当前更像是展示口径容易误解，而不是缓存字段被二次相加。
- 主要放大来源集中在 `~/.codex/sessions` 的本地 Codex JSONL：当天有 `83` 个 session、`12,711` 个 token delta；`model=''` 的旧/子 agent 记录贡献约 `987,868,675`，且 26 个高密度分钟桶贡献同样约 `987,868,675`。后续若要面向用户解释，应把 `总 Token`、`非缓存 Token`、`缓存输入` 和 `observed/projected` 口径拆开显示。
- 用户确认目标是统计真实用量信息。口径结论：subagent 继承上下文如果真实进入模型请求，不能从真实用量中剔除；但 UI 不能把含缓存输入的 `input + output` 直接表述成单一“Token”。已将 projected 摘要改为 `Token(含缓存)` + `非缓存估算` + `输入/缓存/输出`，让真实负载和成本近似口径分开展示。
- 追加根因确认：Codex fork/subagent 启动时会把父线程 rollout history 原样持久化到新线程，历史 `token_count` 被新 JSONL writer 盖上当前启动时间。旧 `parseCodexLocalUsageStream` 从新文件开头 diff 累计 totals，把这些启动历史当作新请求，导致 5-18 约 `987,868,675` token 被重复投影。
- 修复：本地投影解析器现在识别 fork/subagent 启动回放，启动同秒内的父线程历史 `token_count` 只推进累计基线，不写入用量 bucket；同时新增 `RebuildCodexLocalUsageDay(dayKey)` 与 UI“重建当日”，可按本地日期局部重建索引。
- 验收：5-18 单日重建只扫描 `85` 个候选 rollout（不是全量 `3194` 个），重建后本地投影 `input + output = 624,910,855`，`request_count = 4,684`，`input = 623,360,693`，`cached = 588,734,464`，`output = 1,550,162`。这仍高于 sidecar observed `276,809,493`，后续若继续追“真实账单口径”，应继续对齐 observed attribution 与本地 projected 的请求边界差异。
