## 请求重启后短暂变快定位

- 反馈：用户指出重启 GetTokens app 后请求速度只会快几分钟，随后又变慢；本轮只读观察正式进程、日志、SQLite 和源码，没有 kill、重启、替换正式版或修改正式配置数据。
- 证据：正式 sidecar 端口 `8317`，配置目录约 `1.1G`，`sidecar.log` 约 `499M`、`usage-attribution-v1.sqlite` 约 `113M`、`live-sessions-v1.sqlite` 约 `332M`；账号库当前约 `1176` 个活跃 auth-file。`rate_limit_rules` 只有 `token-window/calendar-day/block` 规则，启用 2 条、禁用 1 条，没有 request-window 规则。
- 日志定位：启动后数分钟内出现锁竞争和候选扫描放大，例如 `18:56` 一分钟 `25` 个 `/v1/responses`、`142` 次 route selected、`114` 次 `database is locked/SQLITE_BUSY`、`112` 次 `rate limit admission failed`；`18:57` 一分钟 `123` 次锁竞争、`121` 次 admission failed。后续即使锁竞争下降，`/v1/responses` 仍有 10s+ 请求，说明本地锁竞争是放大器，不是全部上游耗时来源。
- 根因：`RateLimitEvaluator.createRequestWindowReservations()` 先执行 `expireReservations()` 写 `rate_limit_reservations`，再查询当前账号是否存在 request-window block 规则。当前没有 request-window 规则时，这个写锁没有业务价值，却会在大账号池候选入场中被放大，并与 usage attribution 写入、usage summary 读取和 30 秒管理轮询竞争；`admitRequestWindow()` 遇到锁错误返回 active deny，又促使路由继续扫描更多候选。
- 修复：第一刀已在 CLIProxyAPI fork commit `054ea68f fix(gettokens): skip request-window reservations without rules` 落地。`createRequestWindowReservations()` 先查询当前账号启用的 `request-window/block` 规则；没有规则时直接 no-op，不进入 `reservationMu`，不调用 `expireReservations()`，不写 `rate_limit_reservations`。
- 验证：新增红灯/绿灯测试 `TestRateLimitAdmissionNoopsWithoutRequestWindowRulesBeforeReservationWrite`，用 token-window-only 规则和第二 SQLite 连接写锁复现旧实现 `SQLITE_BUSY -> active deny`；修复后 no-op 且 reservation count 为 `0`。已通过 `go test ./internal/gettokenshooks -count=1`、`go test ./internal/gettokenshooks ./internal/gettokensrouting ./sdk/api/handlers/openai -count=1`。已运行 `./scripts/ensure-sidecar.sh darwin arm64`，`build/bin/cli-proxy-api.meta.json` 记录 fork commit `054ea68f958bb6df42414f7df57ffe4ce8255072`、`dirty=clean`。
- 后续补丁边界：第二刀再评估 SQLite busy timeout/WAL、usage/live-session retention 与 sidecar log rotation；上游/模型 10s+ 慢底噪仍需单独归因，本次不把上游慢伪装成本地已解决。
- 沉淀：新增 `docs-linhay/spaces/20260707-request-speed-decay-investigation/README.md` 记录证据门禁与定位结论；`gettokens-performance-governance` 增补 sidecar hot path 规则：admission/routing/quota/rate-limit/usage hooks 必须先证明 no-op path，再做写入、加锁或广泛扫描。
- 本轮沉淀审计：没有新增 AGENTS 或 skill。无规则 fast path 已在 `gettokens-performance-governance` 中有稳定规则，本轮只把具体修复结果、测试和 rebuild 证据写回 space 与 memory。
