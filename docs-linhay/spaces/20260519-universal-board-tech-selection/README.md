# 通用墙面看板技术调研与环境配置

## 背景
计划设计一个 iPad / Mac / iOS / Android 通用的看板系统。典型场景是把 iPad 挂在墙上，用户出门前快速查看天气、日程、之前记录的提醒事项、家庭/个人状态等信息。

本 space 是第一阶段：技术调研、技术选型与本机环境配置。现阶段不直接进入产品开发，先把跨端能力边界、设备常驻能力、天气/提醒数据源、离线与同步策略、构建链路和验收方式确认清楚。

## 目标
1. 明确通用看板系统的第一轮需求边界和验收场景。
2. 对 Flutter、Tauri、React Native / Expo、现有 GetTokens Wails/React 技术栈做技术选型对比。
3. 梳理 iPad 墙挂、macOS 桌面、iPhone、Android 平板/手机的常驻展示与 kiosk 能力差异。
4. 建立本机开发环境检查清单，识别缺口并排定配置顺序。
5. 形成后续需求设计、设计系统稿、开发与冒烟测试的工作入口。

## 范围
1. 平台范围：iPadOS、iOS、macOS、Android。
2. 核心信息范围：天气、提醒事项、时间日期、可扩展信息卡片。
3. 体验范围：墙面远距离可读、出门前快速扫视、低交互或免交互、长时间亮屏、网络异常降级展示。
4. 工程范围：跨端框架、数据层、后台刷新、设备常驻、打包分发、自动化验证、截图验收。

## 非目标
1. 本阶段不实现产品功能。
2. 本阶段不做最终 UI 视觉稿，只定义设计输入和技术约束。
3. 本阶段不接入真实生产账号、真实用户数据或正式天气额度。
4. 本阶段不决定商业化、账号体系和多用户权限模型。

## 验收标准
1. 已创建并补齐本 space 的需求、计划、技术调研文档。
2. 已记录用户确认的开发流程：新建 space -> 设计需求 -> 技术细节补充 -> 回到需求调整 -> 调整设计系统的稿子 -> 执行开发 -> 冒烟测试 -> 交付用户测试。
3. 已完成本机环境初检，并列出必须补齐的工具与风险。
4. 已给出第一轮技术选型候选、推荐验证顺序和待决问题。
5. 已通过文档结构自检；纯文档阶段不运行产品自动化测试。

## BDD 场景
1. 场景：用户早晨出门前查看墙挂 iPad。
   - Given 看板设备处于常亮或可快速唤醒状态
   - When 用户站在门口远距离查看
   - Then 页面应在一屏内展示当前天气、今日提醒和关键状态，不需要复杂操作
2. 场景：网络暂时不可用。
   - Given 设备失去网络
   - When 看板刷新天气或提醒失败
   - Then 页面继续展示最近一次成功数据，并明确标识更新时间或离线状态
3. 场景：跨端验证。
   - Given 同一套看板配置
   - When 在 iPad、macOS、iPhone、Android 上运行
   - Then 信息结构一致，布局按屏幕尺寸适配，核心卡片不被裁切或遮挡
4. 场景：设备常驻。
   - Given 设备用于墙挂或桌面常驻
   - When 用户启用常驻展示模式
   - Then 应尽量减少误触、系统跳出、自动锁屏和电量风险，并在平台不支持时给出可操作说明
