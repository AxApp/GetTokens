### Bug Fix: curl_variables_json 列缺少迁移导致已存在 SQLite 数据库 500

**问题**：写入 credential 时 sidecar 返回 500 错误：
`SQL logic error: no such column: curl variables_json (1)`

**根因**：`curl_variables_json` 列虽然在 `CREATE TABLE` 和 `SELECT/INSERT` 中已定义，但 `EnsureSchema` 函数缺少对应的 `ensureTextColumn` 迁移调用。新建数据库不受影响，但已有数据库缺少该列导致查询失败。

**修复**（sidecar repo `docs-linhay/references/CLIProxyAPI`）：
- `internal/gettokens/accountstore/store.go`: 在 `EnsureSchema` 中添加 `curl_variables_json` 列的 `ensureTextColumn` 调用
- `internal/gettokens/accountstore/store_test.go`: 添加 `TestStoreEnsureSchemaAddsCodexAPIKeyCurlVariablesJSONColumn` 测试，验证 DROP COLUMN 后 EnsureSchema 能恢复列

**验证**：
- 迁移测试通过：模拟已有数据库缺少列，确认 EnsureSchema 自动添加
- Go 全量测试通过（accountstore 模块）
- Sidecar 二进制已重新构建（commit: df370a6f，在 `gettokens/sidecar` 分支）

**教训 & AGENTS.md 更新**：

### Review Fix: relay 模型目录刷新与状态变更错误语义

**问题 1**：OpenAI-compatible / Xiaomi MiMo Token Plan 账号保存了 `modelFetchApiKey` / `modelFetchBaseUrl` 后，账号创建后的 scheduled Codex model catalog refresh 仍用运行时 `tp-*` 凭证和 runtime base URL 拉 `/models`，导致 catalog cache 为空或陈旧。

**修复 1**：`internal/wailsapp/relay_model_catalog.go` 增加 relay 拉模凭证选择逻辑：`ModelFetchBaseURL` / `ModelFetchAPIKey` 非空时优先用于 `/models` 拉取，缺省时分别回退到 runtime `BaseURL` / `APIKey`。新增测试覆盖专用凭证路径和 runtime fallback 路径。

**问题 2**：`SetCodexAPIKeyStatus` 在 sidecar `PatchAccountStatus` 已成功后，如果本地 relay model account cache prune 因 cache 损坏等原因失败，会把 disable 操作返回为失败，并跳过 catalog refresh。

**修复 2**：`internal/wailsapp/accounts.go` 将该路径的 prune 错误改为 log-only，保持状态变更返回成功，并继续调度 Codex model catalog refresh；新增损坏 cache 场景测试验证不返回 prune error 且仍触发 refresh。

**验证**：
- `go test ./internal/wailsapp -run 'TestListRelaySupportedModelsUsesDedicatedModelFetchCredentials|TestListRelaySupportedModelsFallsBackToRuntimeCredentialsWhenModelFetchCredentialsMissing|TestSetCodexAPIKeyStatusIgnoresPruneErrorAndSchedulesRefresh'`
- `go test ./internal/wailsapp`
- `go test ./internal/...`
