## 账号激活/禁用语义修复
- 结论：统一账号激活/禁用确实写入账号卡对应 SQLite 主表记录，即 `account_cards.disabled`；它只代表是否加入账号池路由，不代表账号凭证是否可用。
- 根因：sidecar `PatchAccountStatus` 将 status PATCH 误接到 runtime apply；`SetAccountStatus` 复用会 bump revision 和写 pending apply 的 card 更新路径，导致 apply 失败被前端表现成“激活失败”。
- 修复：`SetAccountStatus` 只更新 `disabled` 和 `updated_at_unix_ms`，不递增 revision、不改 `account_runtime_apply_state`；management status PATCH 不再触发 runtime apply，而是调用轻量 status hook。
- 运行态：status hook 按 `account_key` 同步 runtime route disabled 状态；禁用时写入 `manual-disabled` route guard 并关闭受影响 Codex WebSocket，会让后续请求重新走账号池选择；激活时清除 manual-disabled guard，不主动恢复旧连接。
- 验证：CLIProxyAPI fork 内 `go test ./internal/gettokens/accountstore ./internal/api/handlers/management ./sdk/cliproxy ./sdk/cliproxy/auth -count=1` 通过；已执行 `scripts/ensure-sidecar.sh darwin arm64` 重建本地 sidecar。

## 账号池 quota 与路由热路径边界排查
- 结论：账号池里显示 quota / 额度为 0 只是 Wails/frontend 的资源展示状态，不会自动写入 sidecar 路由热路径的 `Auth.Unavailable`、`AccountRouteGuardStore` 或 channel runtime `rate-limit` source。
- 路由过滤边界：当前 Codex / Claude Channel Routing 候选池只硬过滤手动禁用、runtime 不可用/错误、route guard active block、已尝试账号与 group/scope 条件；quota badge 本身不是 routing guard。
- 风险：若用户看到“无额度账号仍进入路由循环”，这是设计边界造成的状态分层，不是单纯 UI bug；只有真实请求返回 401/402/403/429、上游错误、手动禁用或配置 rate-limit 规则后，才会进入热路径阻断。
- 后续方案：若要改成“quota=0 自动不参与路由”，需先定义 BDD/TDD，明确是前端预览硬过滤、Wails channel runtime source，还是 sidecar-owned 新 `quota-preview` / `rate-limit` guard source，并处理 quota 探测过期导致误杀的风险。

## Account Routing Quota Guard 技术方案
- 决策：新增 sidecar-owned `quota-empty` route guard source；quota/余额是否阻断路由由 sidecar 判断，前端只展示 sidecar 返回的状态。
- reset 语义：fresh quota window `remaining <= 0` 时写入 `quota-empty`，`AccountRouteGuardBlock.ExpiresAt` 使用可靠的 `resetAt`；多个耗尽窗口取最晚 resetAt。
- 风险边界：quota stale、探测失败、未知或未配置 quota 时默认不强阻断，只展示 stale/degraded/unknown，避免误杀可用账号。
- 文档：技术方案落在 `docs-linhay/dev/20260531-account-routing-quota-guard.md`，并已链接到账号路由需求设计 space。

## Account Routing Quota Guard Phase 1 实施
- 实施：CLIProxyAPI fork 新增 `quota-empty` route guard source、quota guard evaluator、runtime `Auth.Quota` 同步与明确 upstream quota error + `RetryAfter` 写入路径。
- 语义：fresh empty window 才强阻断；`ExpiresAt` 使用最晚未来 `resetAt`；stale/degraded/缺失 resetAt/过期 resetAt 不强阻断；恢复时只清理 `quota-empty`，不影响 `manual-disabled` 或 `rate-limit`。
- 热路径：`quota-empty` 进入 account route guard hard-filter，sticky cache 不能复活已过滤账号；Codex WebSocket pinned auth 在 request boundary 命中 `quota-empty` 时释放 pin 并记录 source/reason。

## Account Routing Quota Guard Phase 2 实施
- 实施：CLIProxyAPI fork 新增 sidecar `quota-status` runtime store 与 management API；Wails `GetCodexQuota` 对统一账号会把 quota refresh 结果写入 sidecar quota-status，再使用 sidecar 返回值映射给 UI。
- 语义：fresh success quota window `remaining <= 0` 写入 `quota-empty`，`ExpiresAt` 使用 `reset_at_unix`；auth-file cache fallback 写入 `status=stale`，不会新增强阻断，也不会提前清掉未到 resetAt 的 fresh block。
- 统一数据源：账号池 UI 继续调用既有 `GetCodexQuota`，但返回值已来自 sidecar quota runtime upsert response；路由过滤与 UI 展示先共享 sidecar 结果真源。
- 验证：`go test ./internal/gettokenshooks -run 'TestQuotaRuntime|TestQuotaGuard|TestAccountRouteGuard' -count=1`、`go test ./internal/gettokenshooks ./sdk/cliproxy/auth ./sdk/api/handlers/openai -count=1`、`go test ./internal/cliproxyapi ./internal/wailsapp -count=1` 通过。
